# Архитектура документации KiraCoreAI

## Назначение

Этот файл — карта документации и инструкция по её поддержанию.
Он отвечает на вопрос: **куда идти, что оттуда брать, что проверять и куда вносить изменение**.

Он не заменяет `AGENTS.md`: `AGENTS.md` задаёт процесс работы агента, а этот файл — информационную архитектуру проекта.

## Порядок чтения

`G22.txt` → `AGENTS.md` → нормативные документы `main` → определение платформы → локальный `AGENTS.md` → локальный `STATUS.md` → `ROADMAP.md` → `CHECKLIST.md` → технические документы по маршрутизации.

## Четыре слоя смысла

1. **Целевое** — каким проект должен стать.
2. **Плановое** — каким путём проект должен прийти к цели.
3. **Ожидаемый результат этапа** — что должно быть достигнуто до закрытия этапа.
4. **Фактическое** — что реально существует и подтверждено.

Разница между целевым и фактическим состоянием нормальна на незавершённых этапах. Ошибкой является только смешение уровней или ложное представление промежуточного результата как принятого факта.

## Единый источник

Один класс информации имеет один канонический источник. Остальные документы дают ссылку или производное представление.

## Маршрутизация изменений

- общий архитектурный принцип → `PROJECT-ARCHITECTURE.md` + технический contract;
- цель/этапы → `PROJECT-PLAN.md`;
- конечное/ожидаемое поведение → `PROJECT-BEHAVIOR.md`;
- критерии и фактическое закрытие → `PROJECT-CHECKLIST.md`;
- фактический HEAD/CI/evidence → `MAIN-STATUS.md`;
- ветки/каталоги → `REPOSITORY-STRUCTURE.md`;
- документационная модель → `DOCUMENTATION.md` + при необходимости `AGENTS.md`;
- платформенный план → platform `ROADMAP.md`;
- платформенный факт → platform `STATUS.md`;
- platform verification → platform `CHECKLIST.md`;
- release/pre-release/test-release → platform `README.md` + artifact/release;
- контрольные точки → `MILESTONES.md`;
- временный контекст текущей реорганизации → `паспорт.мд`, пока миграция не завершена.

## Правило актуализации

Если документ создан, удалён, переименован или изменил смысл:
1. обновить `DOCUMENTATION.md`;
2. проверить `AGENTS.md`;
3. проверить соответствующий README/STATUS;
4. проверить дерево ветки.

Не обновлять все документы механически: менять только канонический источник соответствующего класса информации и необходимые производные представления.

## Правило расхождений

- цель может опережать код;
- план может содержать будущие этапы;
- ожидаемый результат относится к конкретному этапу;
- STATUS сообщает только фактически подтверждённое;
- принятие требует отдельного основания.

Если код расходится с документом, сначала определить слой документа и текущий этап. Не считать автоматически код ошибочным и не считать автоматически документ ошибочным.
