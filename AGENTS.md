# AGENTS.md — Кира:Ядро / Android

## Область текущего Android-чата

Этот чат ведётся для Android-контура проекта. Текущая hardening-разработка может выполняться в `android/a2.1-hardening-wip`, а фактическое device evidence фиксируется в `android/alpha-parity`.

Правило:
- изменять прежде всего Android host, Android bridge, Android security/storage boundaries, Android tests и Android-документацию;
- общий Python Core трогать только тогда, когда без изменения общего контракта Android-паритет невозможно реализовать или проверить;
- desktop UI/Windows/Linux runtime не развивать в рамках Android-этапов;
- общие CI/tests могут проверяться как доказательство отсутствия регрессий, но наличие desktop CI job не делает desktop разработкой текущего этапа;
- G22.txt и GENOME/genome.txt не изменять в Android quality/audit cycles.

## Текущий режим разработки с 01.10.2026
Общий архитектурный ledger: `docs/core-architecture-snapshots.md`. Добавлять запись только при изменении общей архитектуры или логического контракта Core; Git остаётся источником полного кода.


До прямого явного указания Алека активный контур проекта — только Android.

## Цель Android-ветки

Создать Android-приложение, функционально эквивалентное настольной Альфе для Windows/Linux.

Под «эквивалентным» понимать прежде всего сохранение поведения KiraCoreAI и его протокольных инвариантов:

- загрузка и проверка активного GENOME;
- раздельные контуры состояния, памяти, истории и разговора;
- локальная персистентность;
- выбор поставщика и модели;
- единый контракт модели;
- генерация ответа через ModelAdapter;
- runtime-ПУЛЬС;
- восстановление последней сессии;
- кандидаты и отдельное утверждение долговременной памяти;
- обработка ошибок без уничтожения ранее сохранённого состояния;
- русскоязычное взаимодействие;
- сохранение границ между геномом, состоянием, памятью, историей, разговором, контекстом и средой.

Android UI не обязан копировать терминальную форму пиксель-в-пиксель. Функциональный контракт важнее формы интерфейса.

### Язык и пользовательский UX Android

Android-интерфейс является самостоятельным пользовательским продуктом, а не графической копией TerminalHost. Он должен быть удобным, функциональным, интуитивным и визуально сдержанным: не перегружать пользователя лишними уровнями навигации и настройками, но предоставлять прямой доступ к реально нужным возможностям Кира.

Русскоязычность распространяется на весь пользовательский контур приложения:

- тексты интерфейса, навигация, кнопки, подсказки и onboarding;
- системные сообщения приложения, ошибки, предупреждения и состояния;
- названия пользовательских действий и настройки;
- справку, диагностику и пользовательские сценарии;
- тексты, которые формирует сам host от имени Кира.

Английский допускается только там, где он является неизбежным техническим идентификатором, собственным именем API/провайдера/модели либо точной внешней цитатой. При наличии естественного русского эквивалента пользовательскому английскому предпочтения нет.

Удобство UI не считается архитектурным расхождением с desktop Alpha. Различия формы интерфейса допустимы и ожидаемы, пока сохраняются наблюдаемое поведение и семантические инварианты ядра.

## Базовая архитектура текущей Альфы

Фактический путь:

```
GENOME/genome.txt
      ↓
GenomeLoader
      ↓
GenomeParser
      ↓
GenomeValidator
      ↓
GenomeRuntimeIndex / GenomeStore
      ↓
StateStore + MemoryStore + HistoryStore + ConversationStore
      ↓
ContextCompiler
      ↓
PromptRenderer
      ↓
ModelAdapter
      ↓
ModelResponse
      ↓
проверка runtime
      ↓
PulseStamp
      ↓
Persistence
      ↓
TerminalHost
```

Android должен заменить или адаптировать прежде всего host-слой, хранение платформенных секретов, ввод/вывод и жизненный цикл приложения. Базовые семантические границы не следует разрушать ради UI.

## Функциональный паритет Альфы

### Запуск

Текущий desktop-путь:

1. определить корень portable-приложения;
2. создать DATA и его подкаталоги;
3. загрузить `GENOME/genome.txt`;
4. распарсить и валидировать геном;
5. создать неизменяемый GenomeStore;
6. восстановить сохранённые сессии, память, историю и разговоры;
7. загрузить настройки и секреты;
8. выбрать коннектор;
9. получить актуальный каталог моделей;
10. выбрать модель;
11. начать/продолжить разговор.

Android должен иметь тот же логический порядок, с платформенным способом хранения файлов и секретов.

### Поставщики моделей

Desktop и Android Alpha используют единый ModelAdapter-контракт, но состав провайдеров платформы различается.

Для Android Alpha задействованы только:
- OpenRouter;
- Google Gemini / Google AI Studio.

LM Studio не входит в Android Alpha.

Единый контракт:

```
ModelCatalogItem
↓
ModelRequest
↓
ModelResponse
```

Конкретный API провайдера не должен протекать в верхние слои.

### Граница Android Alpha по LM Studio

Desktop может использовать локальные OpenAI-compatible endpoints, включая LM Studio.
Android Alpha этого провайдера не включает. Возврат LM Studio в Android Alpha требует отдельного решения и проверки.

### Модель и сессии

Текущая Альфа:

- получает каталог моделей один раз при выборе поставщика;
- фильтрует каталог локально;
- позволяет выбрать модель;
- сохраняет выбранные provider/model в `DATA/preferences.json`;
- предлагает продолжить последний разговор или начать новый;
- сохраняет manifest каждой сессии;
- сохраняет сообщения отдельно от агрегированного состояния.

### Авторизация Алека

Текущий runtime-контракт:

- на первом ходу авторизация активируется, если пользовательский текст равен `~1` или начинается с `~1 `;
- маркер удаляется перед передачей задачи модели;
- после успешной авторизации она хранится в состоянии сессии;
- до авторизации нельзя утверждать память.

Android должен сохранить эту семантику. Способ ввода маркера может отличаться от терминала, но runtime-правило менять без отдельного архитектурного решения нельзя.

### Память

Текущая модель памяти:

```
candidate → explicit approval → approved
```

Модель не имеет прямого пути к утверждённой памяти.

В терминальной Альфе используются:

- `/memory`
- `/memory candidates`
- `/memory approve <id>`

На Android это может быть UI-эквивалент, но обязательны те же семантические состояния и та же проверка авторизации.

### ПУЛЬС

ПУЛЬС генерируется runtime, не моделью.

Формула:

```
series + revision + turn + turn²
```

В текущем коде:

- ревизия = 22;
- серия = 1000;
- ПУЛЬС хранится в состоянии и рядом с ходом разговора;
- ПУЛЬС не является первичным ключом базы;
- модель не обязана и не должна самостоятельно генерировать его.

Android должен получать PulseStamp из core/runtime и отображать его как производный runtime-результат.

### Персистентность

Desktop-структура:

```
DATA/
├── core_state.json
├── preferences.json
├── sessions/
│   └── <session_id>.json
├── conversations/
│   ├── manifest.json
│   └── <session_id>.jsonl
├── memory/
│   └── memory.json
└── history/
    └── history.jsonl
```

Android может хранить эквивалентные данные иначе, но смысл слоёв должен остаться раздельным.

Особенно важно не смешивать:

- полную переписку;
- краткое состояние;
- структурированную долговременную память;
- причинную историю.

## Неизменяемые инженерные инварианты

1. `GENOME/genome.txt` — активный источник истины runtime.
2. `G22.txt` в корне — шаблон разработки; runtime его не читает.
3. Геном не изменяется runtime.
4. Хост не владеет геномом.
5. Модель не владеет утверждённой памятью.
6. Candidate не становится approved автоматически.
7. ПУЛЬС генерируется runtime.
8. Контекст является производным оперативным представлением, а не отдельным источником истины.
9. История и разговор не являются взаимозаменяемыми.
10. Ошибка model-call не должна стирать ранее сохранённые данные.
11. Архитектурные изменения, затрагивающие конституционные правила, нельзя маскировать под Android-порт.

## Процесс разработки и контроль качества

Для Android-ветки действует обязательный поэтапный цикл разработки.

## Текущий этап и переход к A1

### A0.D1 — Device Evidence / Device Acceptance

На этом этапе не изменяется доменная архитектура и не реализуются новые Alpha-функции. Задача — получить воспроизводимое фактическое evidence на vivo X100 Ultra / OriginOS 6 для уже существующего A0.

Допускается временный debug-only Device Evidence Harness, который:
- работает внутри того же Android applicationId и того же packaged KiraCore;
- прогоняет startup → GENOME verification → diagnostics → session → deterministic test turn → Pulse → secure-store round-trip → lifecycle/recovery checks;
- записывает структурированное evidence без секретов;
- экспортирует evidence через системный механизм сохранения файла;
- не получает `MANAGE_EXTERNAL_STORAGE` и не требует полного доступа ко всей файловой системе.

A0.D1 не считается завершённым по факту установки APK. Нужен полученный и проанализированный evidence bundle.

### Gate A0 → A1

Перед началом A1 должны быть выполнены:
- CI #190 остаётся успешным для последнего A0-кодового baseline или его documented successor;
- Device Evidence Harness собирается;
- vivo smoke завершён без критического blocker;
- GENOME revision 22 и SHA-256 совпадают с каноническим значением;
- Python 3.13 / Chaquopy startup подтверждён на устройстве;
- test session / deterministic turn / Pulse подтверждены;
- Keystore round-trip подтверждён;
- process-restart/recovery evidence получено либо оформлено как конкретный blocker;
- evidence bundle проверен на отсутствие секретов;
- документация и checklist обновлены.

Только после этого начинается A1.

### 1. Планирование этапа

Перед началом каждого значимого этапа разработчик:
- изучает актуальный G22/GENOME и связанные контракты;
- проверяет зависимости этапа и входные предпосылки;
- формирует последовательность конкретных шагов;
- фиксирует ожидаемый результат каждого шага;
- отдельно отмечает риски, точки остановки и критерии готовности;
- публикует пользователю краткую предварительную сводку этапа;
- не начинает реализацию, пока пользователь не дал отмашку на этот этап.

Планирование не должно скрывать архитектурные изменения внутри реализации.

### 2. Реализация после отмашки

После подтверждения пользовательского этапа разработка выполняется последовательно:
1. один логический блок;
2. самопроверка;
3. следующий блок;
4. промежуточная проверка зависимостей;
5. фиксация результата в репозитории.

При обнаружении несоответствия уже утверждённой архитектуре разработчик останавливает затрагиваемую часть, исправляет её и не маскирует расхождение как «деталь реализации».

### 3. Итог этапа

После завершения реализации выводится краткий итог:
- что сделано;
- какие файлы/контуры изменены;
- какие проверки проведены;
- что осталось незавершённым;
- какие риски или ограничения обнаружены.

### 4. Обязательный самоаудит

После итогового отчёта пользователь может запросить самоаудит. Самоаудит выполняется отдельно от отчёта о результате и охватывает:
- архитектурную согласованность;
- соответствие G22/GENOME;
- соответствие утверждённым ADR и контрактам;
- корректность зависимостей и границ слоёв;
- безопасность и отсутствие секретов;
- корректность persistence/recovery;
- русскоязычность документации, комментариев и будущих пользовательских сообщений;
- отсутствие устаревшей документации или противоречивых формулировок;
- качество тестов;
- потенциальные ошибки, которые ещё не покрыты автоматикой.

### 5. Финальное тестирование этапа

После самоаудита разработчик выполняет отдельный quality pass:
- тестирует изменённый код;
- проверяет согласованность со смежными слоями;
- сверяет фактическое поведение с документацией;
- проверяет русский язык в комментариях, диагностике, UI-строках и проектной документации;
- проверяет, что итоговые выводы и будущие пользовательские формулировки не противоречат архитектуре;
- обновляет тесты и документацию, если обнаружены расхождения.

Только после этого формируется финальная сводка для решения пользователя.

### 6. Решение пользователя

Пользователь:
- утверждает этап;
- либо возвращает его на доработку с замечаниями.

Следующий значимый этап не считается начатым до утверждения предыдущего результата.

### Разделение ролей

Разработчик самостоятельно принимает обычные инженерные решения в пределах утверждённого архитектурного контракта.

К пользователю выносятся только:
- изменение G22/GENOME;
- изменение конституционных или security-инвариантов;
- изменение identity/privilege model;
- изменение KiraSync protocol;
- изменение состава Alpha;
- архитектурное решение, влияющее на будущие ревизии Кира:Ядра;
- секрет, который принципиально невозможно безопасно получить иначе и который необходим именно на текущем этапе.

### Формат сообщений по этапам

Перед этапом: **план → риски → критерии готовности → запрос отмашки**.

После реализации: **результат → изменённые контуры → проверки → незакрытое**.

После запроса самоаудита: **самоаудит → найденные отклонения → исправления**.

Перед передачей этапа на утверждение: **финальный quality pass → итоговая сводка → решение требуется от пользователя**.


## Секрет авторизации Алека — правило проекта

Пароль не хранится в репозитории и не компилируется в APK/desktop binary.

Он запрашивается только на критическом этапе, когда реализация authority plane требует фактического секрета. Пароль используется для build/provisioning операции, а в результат попадает только sealed/encrypted authority payload и публичные KDF/verifier parameters.

Не допускается:
- запись пароля в Git;
- запись пароля в исходники, build files, resources, логи или telemetry;
- сохранение plaintext-пароля после provisioning/authentication;
- вывод пароля в отчёты или чаты в явном виде;
- использование identity, GENOME или памяти как способа восстановления пароля.

Перед фиксацией authority package обязательны secret scan и аудит build outputs.
