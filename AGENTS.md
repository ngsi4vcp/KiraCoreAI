## Цель Android-ветки

Создать Android-приложение, функционально эквивалентное настольной Альфе для Windows/Linux.

Под «эквивалентным» понимать прежде всего сохранение поведения KiraCoreAI и его протокольных инвариантов:

- загрузка и проверка активного GENOME;
- раздельные контуры состояния, памяти, истории и разговора;
- локальная персистентность;
- выбор поставщика и модели;
- единый контракт модели;
- генерация ответа через ModelAdapter;
- runtime-ПУЛЬС;
- восстановление последней сессии;
- кандидаты и отдельное утверждение долговременной памяти;
- обработка ошибок без уничтожения ранее сохранённого состояния;
- русскоязычное взаимодействие;
- сохранение границ между геномом, состоянием, памятью, историей, разговором, контекстом и средой.

Android UI не обязан копировать терминальную форму пиксель-в-пиксель. Функциональный контракт важнее формы интерфейса.

### Язык и пользовательский UX Android

Android-интерфейс является самостоятельным пользовательским продуктом, а не графической копией TerminalHost. Он должен быть удобным, функциональным, интуитивным и визуально сдержанным: не перегружать пользователя лишними уровнями навигации и настройками, но предоставлять прямой доступ к реально нужным возможностям Кира.

Русскоязычность распространяется на весь пользовательский контур приложения:

- тексты интерфейса, навигация, кнопки, подсказки и onboarding;
- системные сообщения приложения, ошибки, предупреждения и состояния;
- названия пользовательских действий и настройки;
- справку, диагностику и пользовательские сценарии;
- тексты, которые формирует сам host от имени Кира.

Английский допускается только там, где он является неизбежным техническим идентификатором, собственным именем API/провайдера/модели либо точной внешней цитатой. При наличии естественного русского эквивалента пользовательскому английскому предпочтения нет.

Удобство UI не считается архитектурным расхождением с desktop Alpha. Различия формы интерфейса допустимы и ожидаемы, пока сохраняются наблюдаемое поведение и семантические инварианты ядра.

## Базовая архитектура текущей Альфы

Фактический путь:

```
GENOME/genome.txt
      ↓
GenomeLoader
      ↓
GenomeParser
      ↓
GenomeValidator
      ↓
GenomeRuntimeIndex / GenomeStore
      ↓
StateStore + MemoryStore + HistoryStore + ConversationStore
      ↓
ContextCompiler
      ↓
PromptRenderer
      ↓
ModelAdapter
      ↓
ModelResponse
      ↓
проверка runtime
      ↓
PulseStamp
      ↓
Persistence
      ↓
TerminalHost
```

Android должен заменить или адаптировать прежде всего host-слой, хранение платформенных секретов, ввод/вывод и жизненный цикл приложения. Базовые семантические границы не следует разрушать ради UI.

## Функциональный паритет Альфы

### Запуск

Текущий desktop-путь:

1. определить корень portable-приложения;
2. создать DATA и его подкаталоги;
3. загрузить `GENOME/genome.txt`;
4. распарсить и валидировать геном;
5. создать неизменяемый GenomeStore;
6. восстановить сохранённые сессии, память, историю и разговоры;
7. загрузить настройки и секреты;
8. выбрать коннектор;
9. получить актуальный каталог моделей;
10. выбрать модель;
11. начать/продолжить разговор.

Android должен иметь тот же логический порядок, с платформенным способом хранения файлов и секретов.

### Поставщики моделей

В Альфе задействованы:

- OpenRouter;
- Google Gemini через OpenAI-compatible API;
- LM Studio через OpenAI-compatible API.

Единый контракт:

```
ModelCatalogItem
↓
ModelRequest
↓
ModelResponse
```

Конкретный API провайдера не должен протекать в верхние слои.

### Важная оговорка по LM Studio

Desktop-шаблон использует:

```
http://localhost:1234/v1
```

Для Android это не означает автоматически «локальный LM Studio на телефоне». Текущая архитектура лишь требует доступную OpenAI-compatible конечную точку.

Следовательно:

- provider-конракт должен остаться тем же;
- возможность подключения к LM Studio по адресу, доступному с Android-устройства, должна рассматриваться как целевой сценарий;
- нативное локальное выполнение LM Studio на Android **не является зафиксированной возможностью текущего проекта** и не должно объявляться реализованным без отдельной проверки.

### Модель и сессии

Текущая Альфа:

- получает каталог моделей один раз при выборе поставщика;
- фильтрует каталог локально;
- позволяет выбрать модель;
- сохраняет выбранные provider/model в `DATA/preferences.json`;
- предлагает продолжить последний разговор или начать новый;
- сохраняет manifest каждой сессии;
- сохраняет сообщения отдельно от агрегированного состояния.

### Авторизация Алека

Текущий runtime-контракт:

- на первом ходу авторизация активируется, если пользовательский текст равен `~1` или начинается с `~1 `;
- маркер удаляется перед передачей задачи модели;
- после успешной авторизации она хранится в состоянии сессии;
- до авторизации нельзя утверждать память.

Android должен сохранить эту семантику. Способ ввода маркера может отличаться от терминала, но runtime-правило менять без отдельного архитектурного решения нельзя.

### Память

Текущая модель памяти:

```
candidate → explicit approval → approved
```

Модель не имеет прямого пути к утверждённой памяти.

В терминальной Альфе используются:

- `/memory`
- `/memory candidates`
- `/memory approve <id>`

На Android это может быть UI-эквивалент, но обязательны те же семантические состояния и та же проверка авторизации.

### ПУЛЬС

ПУЛЬС генерируется runtime, не моделью.

Формула:

```
series + revision + turn + turn²
```

В текущем коде:

- ревизия = 22;
- серия = 1000;
- ПУЛЬС хранится в состоянии и рядом с ходом разговора;
- ПУЛЬС не является первичным ключом базы;
- модель не обязана и не должна самостоятельно генерировать его.

Android должен получать PulseStamp из core/runtime и отображать его как производный runtime-результат.

### Персистентность

Desktop-структура:

```
DATA/
├── core_state.json
├── preferences.json
├── sessions/
│   └── <session_id>.json
├── conversations/
│   ├── manifest.json
│   └── <session_id>.jsonl
├── memory/
│   └── memory.json
└── history/
    └── history.jsonl
```

Android может хранить эквивалентные данные иначе, но смысл слоёв должен остаться раздельным.

Особенно важно не смешивать:

- полную переписку;
- краткое состояние;
- структурированную долговременную память;
- причинную историю.

## Неизменяемые инженерные инварианты

1. `GENOME/genome.txt` — активный источник истины runtime.
2. `G22.txt` в корне — шаблон разработки; runtime его не читает.
3. Геном не изменяется runtime.
4. Хост не владеет геномом.
5. Модель не владеет утверждённой памятью.
6. Candidate не становится approved автоматически.
7. ПУЛЬС генерируется runtime.
8. Контекст является производным оперативным представлением, а не отдельным источником истины.
9. История и разговор не являются взаимозаменяемыми.
10. Ошибка model-call не должна стирать ранее сохранённые данные.
11. Архитектурные изменения, затрагивающие конституционные правила, нельзя маскировать под Android-порт.

## Приоритет разработки

Сначала добиться минимального сквозного Android-пути:

```
GENOME → startup → provider → model → session → message
→ response validation → PULSE → persistence → restart → resume
```

Затем довести до Android Alpha:

- память;
- история;
- список/возобновление сессий;
- диагностика;
- ошибки;
- настройки;
- OpenRouter;
- Google Gemini.

LM Studio остаётся desktop-коннектором и не входит в Android Alpha.

Не заменять сначала core «красивой мобильной архитектурой». Сначала воспроизвести контракт и проверить его.

## Текущая граница Альфы

У проекта после `0.1.0-alpha.1` ещё не завершены некоторые следующие этапы, зафиксированные в `docs/roadmap.md`:

- внешняя smoke-проверка реальной Альфы;
- структурированный extractor кандидатов памяти;
- восстановление незавершённого model-call;
- streaming;
- контракт инструментов и runtime;
- сценарная оценка дрейфа.

Не включать эти функции в формулировку «уже реализовано» только потому, что Android-ветка создаётся позднее.

## Безопасность Android и Core

Не путать семантическую саморефлексию с cryptographic authority.

Модель получает только safe constitutional projection и capabilities текущей сессии. Полный текст защищённых секций GENOME, пароль, verifier и key material в ModelRequest не попадают.
