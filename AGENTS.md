# AGENTS.md — KiraCoreAI / общая рабочая инструкция

## 0. Обязательный старт

Перед любой работой:

1. Прочитать `G22.txt`.
2. Прочитать все канонические нормативные документы `main`, указанные в `DOCUMENTATION.md`.
3. Определить, относится ли задача к общему Core или к конкретной платформе.
4. Если нужна платформенная работа — перейти только после чтения `AGENTS.md`, `STATUS.md`, `CHECKLIST.md` и `DOCUMENTATION.md` целевой платформенной ветки.
5. Проверить фактический Git/HEAD, дерево файлов и актуальные тестовые/CI-доказательства.
6. Сверить фактическое состояние с документацией и отдельно распознать: целевое, плановое, ожидаемый результат этапа и фактическое.

Документация не заменяет проверку репозитория. Код не заменяет проектную цель.

## 1. Канонические документы main

До перехода в любую платформенную ветку агент обязан ознакомиться со всей нормативной документацией `main`. Технические документы `docs/*` читаются по маршрутизации `DOCUMENTATION.md` и дополнительно по требованиям текущей задачи; нормативная карта и её правила должны быть поняты до перехода в платформу.

Порядок чтения:

1. `G22.txt`;
2. `AGENTS.md`;
3. `PROJECT-RULES.md`;
4. `DOCUMENTATION.md`;
5. `PROJECT-ARCHITECTURE.md`;
6. `PROJECT-PLAN.md`;
7. `PROJECT-BEHAVIOR.md`;
8. `PROJECT-CHECKLIST.md`;
9. `MAIN-STATUS.md`;
10. `REPOSITORY-STRUCTURE.md`;
11. технические документы из `docs/` — по маршрутизации `DOCUMENTATION.md`.

Перед переходом в платформенную ветку обязательно прочитать её локальный `AGENTS.md`, `STATUS.md`, `ROADMAP.md`, `CHECKLIST.md`.

## 2. Семантика документов

- Целевое: каким проект должен стать.
- Плановое: каким путём проект должен прийти к цели.
- Ожидаемый результат этапа: проверяемый результат конкретного промежуточного шага.
- Фактическое: что реально существует и чем подтверждено.

Наличие пункта в целевой архитектуре не означает его реализации.
Наличие пункта в плане не означает его выполнения.
Статус «реализовано» не означает «принято».

## 3. Обязательный рабочий цикл

1. Изучить контекст и документы.
2. Проверить реальное состояние репозитория.
3. Найти расхождения между документацией и фактом.
4. Определить текущий разрешённый этап.
5. Сформулировать цикл: цель → шаги → критерии → риски → граница остановки.
6. Выполнять шаги последовательно.
7. После существенного шага делать самопроверку.
8. Проверять зависимости между Core и платформой.
9. Провести quality pass.
10. Обновить документацию по правилам `DOCUMENTATION.md`.
11. Повторно сверить документацию с кодом.
12. Сформировать фактический отчёт.

## 4. Разрешение расхождений

При конфликте:

- фактический статус должен отражать фактическое состояние;
- целевой документ может опережать код;
- план может содержать ещё не реализованные этапы;
- обязательный результат уже принятого этапа не должен молча расходиться с реализацией;
- обнаруженная незапланированная реализация не становится автоматически новым планом;
- агент фиксирует проблему и либо исправляет её в пределах разрешённого этапа, либо выносит решение пользователю.

Нельзя «дорисовывать» реализацию по документации и нельзя считать код неверным только потому, что он ещё не достиг конечной цели проекта.

## 5. Инженерные инварианты

Не изменять G22/GENOME без отдельного разрешения.
Не смешивать GENOME, MEMORY, HISTORY, STATE, CONTEXT и ENVIRONMENT.
Не выдавать целевое состояние за факт.
Не скрывать ограничения среды под видом личного решения.
Не считать тестовое доказательство автоматически приемкой.
Не считать сборку приложения доказательством функционального паритета.

## 6. Ветвление

Актуальная долгоживущая схема:

- `main` — общий Core и общая архитектурная база;
- `platform/android` — Android-обвязка и Android-специфическая реализация;
- `platform/windows-11` — Windows 11 реализация;
- `platform/linux` — Linux реализация;
- `archive/history` — исторический архив.

Долгоживущих временных веток нет. Краткоживущая рабочая ветка допустима только при технической необходимости и должна быть устранена в рамках текущего цикла.

## 7. Core-поток

Если изменение требуется общему Core:

1. реализовать его в `main`;
2. покрыть Core-тестами в `main`;
3. после принятия подтянуть Core в активную платформенную ветку;
4. в платформенной ветке отдельно выполнить Core+Platform проверки.

Не переносить платформенную семантику обратно в Core только ради удобства конкретного host.

## 8. CI и доказательства

Core-тесты выполняются отдельно в `main`.
Платформенные ветки запускают Core+Platform тесты, чтобы не расходовать общий суточный лимит раннера на повторение одного и того же полного цикла.

Acceptance имеет три разные оси:
- реализовано;
- проверено;
- принято.

## 9. Документация

Правильный документ определяется через `DOCUMENTATION.md`.
Один класс информации имеет один канонический источник.
При изменении состава или смысла документации сначала/одновременно обновляется `DOCUMENTATION.md`.
