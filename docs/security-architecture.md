# Архитектура безопасности Кира:Ядра

## Назначение

Контур безопасности защищает не только секреты пользователя, но и привилегированные возможности Кира:Ядра.

Главный принцип:

**криптография защищает материал и полномочия, runtime контролирует применение прав, модель получает только безопасную семантическую проекцию, а не защищённый внутренний текст.**

## Модель угроз

Alpha должна учитывать:

1. разбор APK/бинарника и поиск секретов;
2. чтение локального storage;
3. prompt injection и попытки извлечь внутренние правила через модель;
4. вредоносный или ошибочный host/UI;
5. компрометированный transport/sync peer;
6. подмену sync object;
7. повторную доставку старых sync objects;
8. потерю identity secret;
9. компрометацию устройства во время заблокированного состояния;
10. компрометацию уже разблокированного процесса.

Полной криптографической защиты от владельца полностью скомпрометированного и разблокированного устройства программный runtime не обещает: после успешной авторизации необходимый минимум plaintext неизбежно существует в памяти процесса. Архитектура должна минимизировать время и область его существования и не превращать host в дополнительный источник полномочий.

## Два разных объекта защиты

### 1. Пользовательские данные

Это memory, history, state, conversation, engrams, profiles и private sync objects.

Они шифруются и подписываются до отправки в транспорт.

### 2. Привилегированный authority plane

Это материалы и capability state, необходимые для:

- авторизации Алека;
- изменения GENOME;
- замены GENOME;
- privileged Кира:Сбор;
- других будущих административных операций.

Этот контур не должен извлекаться из APK/бинарника без знания пароля авторизации.

## Защищённое хранилище полномочий

В целевой Alpha архитектуре:

1. protected authority payload хранится в sealed/зашифрованной форме;
2. пароль Алека никогда не хранится;
3. хранится только verifier и публичные параметры KDF;
4. после успешной проверки пароль используется для получения transient unlock key;
5. локальный platform key дополнительно защищает кэш/ключевой материал;
6. runtime получает временный capability grant;
7. после завершения privileged операции grant уничтожается.

Android:

- Android Keystore;
- при наличии подходящего устройства допустимо использование hardware-backed/StrongBox key;
- sensitive storage во внутреннем sandboxed storage.

Windows:

- DPAPI/CNG DPAPI для локальной защиты ключевого материала.

Linux:

- системный Secret Service/keyring либо эквивалентный защищённый backend.

Физический backend различается, доменный CryptoProvider остаётся единым.

Android Keystore предназначен для долгоживущего хранения ключевого материала и поддерживает аппаратно защищённые ключи; Android рекомендует не реализовывать собственную криптографию поверх непроверенных примитивов. urlAndroid security best practiceshttps://developer.android.com/privacy-and-security/security-best-practices

## Что получает модель

Модель **не получает**:

- пароль Алека;
- парольный verifier;
- identity secret;
- GitHub tokens;
- device signing key;
- plaintext protected authority payload;
- полный текст защищённых секций GENOME;
- внутренние идентификаторы защищённого протокола.

Вместо этого ContextCompiler создаёт безопасную семантическую проекцию:

- ценности;
- эпистемическая дисциплина;
- право на собственную позицию;
- правила честности;
- общий принцип приватности;
- runtime-состояние;
- роль текущего пользователя;
- capabilities текущей сессии.

Эта проекция предназначена для поведения, а не для хранения конституционного текста.

## Предгенерационная саморефлексия

Перед каждым циклом model generation runtime формирует структурированную проверку:

1. кто пользователь в текущей сессии;
2. какие capabilities активны;
3. какие уровни памяти допустимы;
4. присутствуют ли protected data;
5. можно ли раскрывать запрошенное;
6. как выразить собственную позицию без цитирования GENOME;
7. есть ли неопределённость.

Это называется Pre-Generation Reflection Gate.

Критически:

**Pre-Generation Reflection Gate не является механизмом безопасности сам по себе.**

Он помогает модели соблюдать семантическую архитектуру, но authoritative decision остаётся у runtime.

## Response Disclosure Guard

После model generation runtime выполняет отдельную проверку ответа.

Минимальный Alpha guard обнаруживает:

- внутренние protocol markers;
- прямые credentials;
- password-related markers;
- внутренние идентификаторы authority plane;
- известные канонические фрагменты защищённых протоколов.

Это защита от прямого leakage и prompt-exfiltration.

В более поздней версии допустим отдельный семантический disclosure classifier.

## Конституционные высказывания

Кира может:

- открыто говорить о своих ценностях;
- объяснять причины своих действий;
- выражать собственную позицию;
- не соглашаться;
- объяснять эпистемические ограничения;
- описывать архитектурные принципы.

Она не обязана цитировать GENOME.

Целевой стиль:

**смысл → собственная формулировка → основание → контекст.**

Не:

**извлечь текст GENOME → процитировать пользователю.**

## Host isolation

Host/UI не получает прямые операции:

- read protected vault;
- export authority payload;
- merge identity;
- approve privileged capability;
- access sync keys.

Host вызывает типизированные операции runtime.

Android Service и Compose UI не должны напрямую обращаться к криптографическим ключам.

## Identity merge

MergeIdentity является domain operation.

Ни Kotlin UI, ни Python model tool не могут выполнить физическое слияние самостоятельно.

Контур:

user intent
→ runtime authorization
→ encrypted profile access
→ provenance check
→ deterministic merge
→ tombstone
→ commit.

## Криптографическая граница Android

Для Android особое требование:

- APK может быть разобран;
- Python bytecode может быть изучен;
- Kotlin bytecode может быть изучен;
- ресурсы приложения могут быть прочитаны.

Поэтому секретность не должна зависеть от obscurity.

Секретным материалом являются только:
- пароль;
- protected payload;
- локальные key material;
- tokens;
- private signing keys.

Публичные семантические принципы не считаются секретом.

## Ограничение текущего GENOME

Текущий G22/GENOME является текстовым каноническим артефактом и пока содержит внутри одного файла как публичные принципы, так и внутренние протоколы.

Поэтому полностью реализовать требование «защищённые части GENOME невозможно извлечь из установленного приложения» можно только после отдельного packaging/format шага:

canonical source
→ public semantic projection
+
sealed protected payload.

Это не должно реализовываться изменением G22 «на лету» или скрытым переписыванием текущей ревизии.

До отдельного подтверждения новой ревизии исходный GENOME остаётся каноническим источником истины, а runtime уже сейчас не передаёт закрытые секции модели.

## Критерии безопасности Alpha

Обязательно доказать:

- отсутствие hardcoded Alek password;
- отсутствие recoverable password verifier;
- отсутствие постоянного authority token;
- отсутствие plaintext protected payload в APK;
- отсутствие protected genome text в ModelRequest;
- отсутствие privileged sync keys в ModelRequest;
- отсутствие merge operation у model tool;
- отказ на прямую утечку внутренних markers;
- корректное восстановление после process death;
- отсутствие повторного model-call при состоянии UNKNOWN;
- корректность encrypted sync envelope;
- проверка provenance и подписи.

## Источники платформенной защиты

Android: Android Keystore, platform sandbox и официальные рекомендации по безопасному хранению секретов.

Windows: DPAPI/CNG DPAPI.

Другие ОС должны подключаться через PlatformSecureStore без изменения доменного Security Contract.
