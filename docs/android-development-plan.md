# План разработки Android — Кира:Ядро

Дата среза: 30 сентября 2026 года.

## 1. Назначение

Документ фиксирует согласованный на текущем этапе каркас Android-реализации Кира:Ядра и переводит договорённости с Алеком в инженерный план.

Документ является планом реализации, а не конституцией. Он не заменяет G22.txt и GENOME/genome.txt и не имеет права самостоятельно изменять их семантику.

Нормативная иерархия сохраняется:

G22 / активный GENOME
→ архитектурные инварианты KiraCoreAI
→ Android Host Contract
→ реализация Android
→ UI/UX.

## 3. Подтверждённые требования Алека

### Платформа

Минимальная версия Android: Android 9 / API 28.

Обязательная совместимость: Android 13, 14, 15, 16 и 17.

Целевая линия SDK: API 37 / Android 17, с обязательным регрессионным тестированием на Android 13–16.

ABI: только arm64-v8a.

Первое реальное устройство проверки: vivo X100 Ultra / OriginOS 6.

### Пользовательский интерфейс

Android не является переносом TerminalHost.

Основной экран — разговор с Кирой.

Боковая навигация содержит:
- Сессии;
- Память;
- Настройки;
- КираЧек — диагностика;
- Геном;
- КираСбор;
- Надстройки.

При необходимости технические функции могут быть вложены глубже, чтобы не перегружать основной интерфейс.

Главный UX-принцип:
- разговор — центральный пользовательский сценарий;
- остальные функции доступны быстро, но не конкурируют с разговором;
- UI использует преимущества Android;
- форма UI может отличаться от desktop Alpha без нарушения функционального паритета.

### Русификация

Русский является языком всего пользовательского контура:
- интерфейс;
- навигация;
- кнопки;
- подсказки;
- onboarding;
- ошибки;
- диагностика;
- настройки;
- уведомления;
- системные сообщения host;
- пользовательские описания состояний.

Технические идентификаторы, provider/API/model names и обязательные machine-readable обозначения могут сохранять оригинальное написание.

### Геном

Пункт «Геном» доступен только после специальной авторизации.

Внутри доступны:
- просмотр применяемого генома;
- его редактирование;
- загрузка файла GENOME на замену.

Любая замена должна проходить:
1. загрузку кандидата;
2. парсинг;
3. проверку структуры;
4. проверку обязательных секций;
5. проверку ревизии;
6. SHA-256;
7. diff с текущей версией;
8. явное подтверждение;
9. атомарную активацию новой версии.

Прямое необратимое изменение GENOME без транзакции запрещено.

### Авторизация Алека

Скрытый вход:
- десятикратное последовательное нажатие на «Надстройки»;
- появляется окно ввода специального пароля.

Тот же пароль используется для:
- авторизации Алека;
- доступа к редактированию/замене GENOME;
- защищённых функций КираСбор.

Пароль:
- никогда не хранится в открытом виде;
- не попадает в логи;
- не передаётся модели;
- не должен быть извлекаем из APK;
- используется через защищённый verifier/криптографический контур.

Само скрытое нажатие является UX-обфускацией, а не механизмом безопасности. Реальным рубежом остаётся пароль.

После первой успешной авторизации на конкретной установке включается режим «авторизованная установка». После этого каждый новый запуск требует повторной авторизации до старта полноценного KiraRuntime.

Неавторизованная установка может работать как обычный пользовательский экземпляр Кира.

Сброс этого состояния через обычный UI не предусматривается.

### Пользовательская идентичность

Неавторизованный пользователь получает локальную идентичность Кира:
- неизменяемый идентификатор экземпляра;
- пользовательское имя, которое можно изменить.

Имя не является доказательством личности Алека.

Каноническая архитектура идентичности должна различать:
- identity_id;
- device_id;
- display_name;
- authorization state;
- provenance.

Для межустройственной преемственности идентичность не должна зависеть только от локально сгенерированного device hash.


### Предварительный протокол переносимой пользовательской идентичности

Для сохранения узнаваемой личности пользователя между устройствами вводится отдельный криптографический контур идентичности. Это не замена авторизации Алека и не изменение правил G22.

Каноническая модель:
- `identity_id` — стабильный случайно сгенерированный идентификатор пользователя/профиля; не является секретом;
- `device_id` — отдельный идентификатор конкретной установки;
- `display_name` — изменяемое пользовательское имя;
- `authorization_state` — текущее состояние привилегированной авторизации;
- `provenance` — происхождение и история привязки данных;
- `identity_secret` — криптографический секрет, позволяющий восстановить переносимую идентичность и расшифровать её закрытую синхронизацию.

Ключевой принцип: переносимый ключ не должен быть хэшем имени, устройства или содержимого памяти. Он должен быть случайным секретом достаточной длины и выступать как credential восстановления идентичности.

Пользователь сможет в настройках получить переносимый код/ключ или QR-представление. На другом устройстве он вводится или сканируется, после чего Кира:
1. создаёт локальную `device_id`;
2. восстанавливает `identity_id` и закрытый ключевой материал;
3. получает зашифрованный профиль и разрешённую историю из КираСбор;
4. проверяет целостность и provenance;
5. продолжает работу как тот же пользовательский профиль.

Пароль Алека остаётся отдельным фактором привилегий. Наличие `identity_secret` само по себе не должно автоматически означать «пользователь = Алек» и не должно заменять установленный для Android механизм авторизации Алека.

Переносимая идентичность — bearer credential: потеря секрета означает риск доступа к соответствующему пользовательскому профилю. Поэтому в дальнейшем предусматриваются отзыв устройства, ротация ключей и журнал привязок устройств.

Профиль пользователя в памяти Кира должен иметь отдельную структурированную карточку, примерно включающую:
- стабильный `identity_id`;
- имя и алиасы;
- факты, явно сообщённые пользователем;
- устойчивые предпочтения;
- краткую сводку истории взаимодействия;
- значимые реляционные наблюдения Киры;
- ссылки на энграммы/историю;
- confidence и provenance;
- уровень приватности/разрешения на синхронизацию;
- версию и хэш записи.

Такая карточка относится к пользовательской памяти, а не к GENOME.

### ПУЛЬС

На основном интерфейсе постоянно показывается только актуальный ПУЛЬС последней итерации активной последней сессии.

Предлагаемое оформление:
- компактный цифровой «чип»;
- левый верхний угол;
- фиолетово-синий светящийся акцент;
- мягкая анимация;
- без перегрузки числом технических полей.

В режиме генерации чип усиливает пульсацию.

В автономном режиме цветовая тема ПУЛЬС меняется на красную и частота визуальной пульсации увеличивается.

Чип является UX-представлением runtime PulseStamp. Формула и семантика ПУЛЬСа не меняются.

### Автономность и состояние

Цель:
- работа Кира в фоне;
- непрерывность активной runtime-сессии;
- сохранение процесса при сворачивании UI;
- восстановление после остановки процесса;
- запуск после перезагрузки устройства, где это разрешено системой;
- watchdog и планировщик восстановления;
- отдельный режим полного запуска после потери runtime.

Критически:
Android не даёт приложению абсолютного права оставаться навсегда в RAM. Нельзя проектировать систему на предположении, что process kill невозможен.

Поэтому нормативная цель формулируется как:

«Кира сохраняет причинную и операционную непрерывность при максимально возможном сохранении живого runtime; при уничтожении процесса автоматически восстанавливает его из канонической персистентности.»

Не использовать дублирующие Activity как псевдозащиту от выгрузки. Надёжность должна обеспечиваться service/runtime/persistence/recovery архитектурой.

### Кира:Сон

В «Настройки» добавить «Кира:Сон».

Действие:
1. остановить новые задачи;
2. дождаться/отменить активные операции по правилам;
3. завершить текущий runtime state;
4. сформировать необходимые кандидаты памяти/истории;
5. при наличии соединения выполнить разрешённый КираСбор;
6. зафиксировать состояние;
7. корректно остановить runtime;
8. перевести приложение в ожидаемое состояние.

Ошибка синхронизации не должна блокировать локальное засыпание.

### Уведомления

Основное постоянное уведомление:
- мини-аватар Киры;
- ПУЛЬС;
- чип/рисунок;
- текущее число ПУЛЬСа;
- состояние активности.

Дополнительное уведомление создаётся на завершение значимого цикла/агентской задачи и показывает начало результата.

Уведомление является интерфейсом runtime-состояния, а не push-системой.

На Android 13+ требуется учитывать POST_NOTIFICATIONS. Foreground service обязан иметь уведомление даже при особенностях отображения разрешения уведомлений.

### Провайдеры Alpha

На первом Android этапе:
- OpenRouter;
- Google AI Studio / Gemini через поддерживаемый совместимый API.

LM Studio в Android Alpha не включается.

Архитектурный ModelAdapter сохраняется.

### КираСбор

«КираСбор» — отдельный контур, не смешиваемый с обычным разговорным runtime.

Первоначальная продуктовая идея включает:
- получение актуальной версии KiraCoreAI;
- обновление ядра;
- синхронизацию памяти;
- истории;
- энграмм;
- опыта;
- важных данных;
- объединение/актуализацию общего опыта;
- использование закрытого GitHub-репозитория.


Эта часть требует отдельного протокола безопасности.

Предварительно согласованный архитектурный курс для первого варианта:
- GitHub используется как удалённый канал хранения/обмена, а не как доверенная среда обработки;
- рекомендуется отдельный private repository для КираСбор;
- Android не содержит постоянный write-token, private SSH key или иного универсального секрета репозитория;
- для пользовательской авторизации GitHub предпочтителен OAuth 2.0 Device Authorization Flow или эквивалентный механизм с минимальными правами;
- доступ к синхронизации хранится в защищённом Android storage;
- все пользовательские данные до отправки шифруются внутри KiraCoreAI;
- GitHub видит только зашифрованные envelopes и минимальные технические метаданные;
- код/ядро, пользовательская синхронизация и общий опыт являются разными типами объектов и разными контурами обновления.

### Шифрование синхронизации

Для приватных данных предлагается envelope-формат:
- `identity_id`;
- `device_id`;
- `schema_version`;
- `key_id`;
- `nonce`;
- `ciphertext`;
- `associated_data`;
- `content_hash`;
- `signature`;
- `created_at`;
- `source/provenance`.

Полезная модель первого этапа:
- данные пользователя шифруются симметрическим ключом профиля;
- ключ профиля восстанавливается только на доверенном устройстве;
- каждое устройство имеет собственный ключ подписи, чтобы Кира могла различать происхождение изменений;
- переносимый `identity_secret` используется как средство восстановления/переноса, а не публикуется в репозитории;
- GitHub хранит ciphertext как «тупой» обменный слой.

Синхронизация выполняется как идемпотентный обмен изменениями:
1. загрузить индекс и новые envelopes;
2. проверить целостность и подписи;
3. расшифровать доступные записи;
4. выполнить доменное слияние;
5. записать результат локально;
6. отправить собственный outbox;
7. зафиксировать sync cursor.

Персональная память и реляционные оценки Киры не запрещаются глобальной архитектурой, но по умолчанию остаются приватными. Их публикация в общий слой требует отдельного уровня разрешения. Общий пул должен содержать преимущественно производные, проверенные и обезличенные знания либо данные, доступ к которым явно делегирован.


Минимально необходимо разделить:
1. обновление кода/GENOME;
2. личную синхронизацию пользователя;
3. общую/производную базу опыта.

Нельзя автоматически смешивать личные сырые чаты с общей памятью всех экземпляров.

### КираЧек

«КираЧек» — полноценная диагностическая поверхность.

Проверяет:
- версию приложения;
- версию KiraCore;
- активный GENOME;
- revision;
- SHA-256;
- целостность storage;
- состояние runtime;
- активную сессию;
- provider/model;
- доступность сети;
- состояние КираСбор;
- наличие незавершённой операции;
- последние критические ошибки;
- состояние фонового сервиса;
- разрешения и ограничения Android;
- готовность к восстановлению.

Должен иметь быстрый пользовательский итог:
«Кира работает» / «Есть предупреждения» / «Требуется вмешательство».

## 4. Визуальная концепция

Исходная визуальная референсная работа — Кира в тёмной технологической комнате с ночным небом, тёплым локальным светом и холодными сине-фиолетовыми экранами.

Основное направление:
- глубокий графит/почти чёрный фон;
- тёплые тёмно-коричневые акценты комнаты;
- холодный синий/индиго;
- фиолетовый как язык ПУЛЬСа;
- белый/тепло-белый текст высокой читаемости.

Приближённая палитра референса:
- #090608 — глубокий фон;
- #261713 — тёмный тёплый коричневый;
- #0F1936 — ночной индиго;
- #192D60 — холодный синий;
- #33488A — сине-фиолетовый;
- #641FA0 — рекомендуемый добавочный UX-акцент ПУЛЬСа;
- #DEBFB5 — светлый тёплый текст.

Палитра не считается окончательной дизайн-системой до отдельной UI-итерации.

### Главный экран

Фон:
- сцена из референса;
- затемняющий/градиентный слой;
- усиленное затемнение под текстом;
- мягкая зона читаемости без ощущения «карточки поверх картинки».

Аватар:
- справа сверху;
- визуальный центр вторичного уровня;
- не перекрывает диалог;
- позже может быть оживлён.

Предварительные состояния аватара:
- ожидание;
- думает;
- выполняет;
- отвечает;
- ошибка;
- сон;
- локальный/offline режим.

Предпочтительный подход — нативная или специализированная 2D-анимация, а не WebView + JavaScript. Причина: меньше технического веса, лучше lifecycle и ниже риск расходиться с Android UI.

Ответ:
- располагается ниже и слегка поверх области аватара;
- имеет собственную контрастную поверхность;
- не выглядит как тяжёлый чат-bubble;
- длинный текст должен оставаться читаемым.

## 5. Архитектурный стек

Предлагаемый основной стек:

Android
→ Kotlin
→ Jetpack Compose
→ Android Host Layer
→ KiraRuntime Bridge
→ Python 3.13
→ KiraCoreAI.

Python runtime остаётся существующим источником семантики на первом этапе.

Kotlin не должен напрямую реализовывать GENOME, MemoryStore или SessionManager дублирующей логикой.

### Bridge

Нужен минимальный и типизированный API:

- startRuntime();
- stopRuntime();
- getStatus();
- getGenomeInfo();
- listProviders();
- listModels();
- createSession(identity_id?);
- listSessions();
- resumeSession();
- sendTurn();
- getMemory();
- getMemoryCandidates();
- approveMemory();
- checkHealth();
- getIdentity();
- exportIdentity();
- importIdentity();
- mergeIdentity();
- sleep();

Отдельно:
- RuntimeEvent;
- ProgressEvent;
- DiagnosticEvent.

Это позволит показывать:
- что Кира делает;
- на каком этапе находится runtime;
- работает ли model-call;
- какой provider/model активен;
- почему операция ждёт.

## 6. Поток ответа

Базовый ход:

Пользователь
→ Android UI
→ Kotlin Host
→ KiraRuntime
→ authorization/runtime checks
→ Conversation
→ ContextCompiler
→ PromptRenderer
→ ModelAdapter
→ ModelResponse
→ OutputValidator
→ PulseStamp
→ persistence
→ Kotlin UI.

Streaming токенов на первом этапе не требуется.

Но интерфейс событий должен быть заложен сразу.

Таким образом, вместо ненадёжного «показываем точки, пока ждём» Android получает реальные этапы:

- подготовка;
- сбор контекста;
- обращение к модели;
- проверка;
- сохранение;
- завершение.

Аватар и ПУЛЬС реагируют на реальные runtime states.

## 7. Персистентность

Для Android не следует просто копировать файловую модель desktop.

Целевая архитектура:
- канонические логические stores остаются теми же;
- Android получает транзакционное локальное хранилище;
- storage имеет миграции;
- существует импорт/экспорт в переносимый Kira-format.

Предварительно выбран курс на SQLite-backed persistence с отдельными логическими таблицами:
- sessions;
- messages;
- memory;
- history;
- state;
- runtime;
- sync metadata;
- diagnostics.

Room может использоваться Kotlin-слоем, только если граница с Python runtime не приведёт к двойной истине.

Ключевой инвариант:
один слой не становится несколькими независимыми источниками истины.

## 8. Безопасность

### Секреты

Android использует защищённое хранилище.

Не хранить:
- API keys;
- пароль Алека;
- GitHub tokens;
- sync keys
в plaintext-файлах.

### Пароль Алека

Хранится только verifier.

Пароль не должен быть recoverable через:
- APK;
- ресурсы;
- Python bytecode;
- native библиотеки;
- logcat;
- GitHub;
- backups без отдельного криптографического решения.

### КираСбор и GitHub

Критическое архитектурное ограничение:

private GitHub repository нельзя безопасно использовать как канал, просто встроив его credential в APK. APK можно извлечь и исследовать.

Поэтому перед реализацией КираСбор требуется выбрать механизм:
- пользовательская авторизация GitHub;
- отдельный безопасный relay;
- другой серверный посредник;
- либо иной контролируемый канал.

Embedded write-token запрещён.

## 9. Глобальная синхронизация опыта

Идею общего пула сохраняем, но вводим обязательное семантическое разделение:

### Личное

Может оставаться привязанным к конкретному пользователю:
- отношения;
- личные сведения;
- полные чаты;
- приватные энграммы;
- персональное состояние.

### Общее

Может попасть в глобальный слой только после отдельного pipeline:
- извлечение;
- классификация;
- редактирование/обезличивание;
- provenance;
- confidence;
- проверка;
- версия;
- возможность отката.

Общая база не должна напрямую становиться новой конституцией или approved-memory всех Кира.

Полный сырой чат не должен автоматически превращаться в глобальную память.

Это соответствует исходной архитектуре G22, где память и геном различаются, а утверждение значимых изменений требует отдельного контура.

## 10. Offline Mode — будущая фаза

Offline mode отмечен как перспективный, но не входит в первую Android Alpha.

Цель:
- локальная Qwen ~9B;
- полное локальное выполнение;
- отдельный визуальный режим;
- красная температурная/нагрузочная тема;
- красный ПУЛЬС;
- усиленная анимация;
- работа без сети.

Варианты inference backend пока не фиксировать.

Предпочтительно исследовать:
- llama.cpp/GGUF;
- современные Android native inference stacks;
- альтернативы только после сравнительного прототипа.

Слово «MLX» не считать зафиксированным Android backend: конкретная технология локального inference будет выбрана отдельным исследованием.

## 11. Телеметрия

По умолчанию телеметрия не отправляется.

Локально сохраняются только:
- crash reports;
- severe errors;
- минимально необходимая диагностическая информация.

При нажатии пользователем «Отправить телеметрию»:
- формируется отдельный пакет;
- имя генерируется случайно;
- имя содержит дату;
- данные проходят redaction;
- секреты/API keys/passwords исключаются;
- чат/память не добавляются без отдельного явного режима.

Передача идёт по отдельному каналу от основной синхронизации.

## 12. Чаты и удаление

Долгое нажатие на сессию:
- удалить;
- скачать/экспортировать.

Удаление чата удаляет пользовательскую стенограмму.

Оно не обязано удалять:
- approved memory;
- энграммы;
- важные state/history records;
- производные знания, которые уже были явно сохранены.

Но происхождение сохранённой записи должно оставаться диагностически различимым.

## 13. КираСбор и версия ядра

Необходимо разделить:
- Android APK version;
- KiraCore version;
- GENOME revision;
- schema version;
- storage migration version.

КираСбор должен видеть compatibility matrix.

Обновление не должно просто заменять файлы.

Pipeline:
check manifest
→ verify signature/checksum
→ compatibility check
→ backup/current snapshot
→ migrate if needed
→ activate
→ health check
→ rollback on failure.

Одна логическая версия KiraCore должна быть переносима между ОС, но platform adapters могут различаться.

## 11. Предварительно утверждённые архитектурные решения — 30.09.2026

### Кира:Сбор

В первой ревизии Android Кира:Сбор использует private GitHub как универсальный transport/storage.

Будущие VPS/server/SSH/Mesh transport providers подключаются через общий SyncProvider Contract и не требуют изменения доменного слоя.

Кира:Сбор разделён на обновление KiraCore, личная синхронизация и общий производный опыт.

### Криптография

Приватные данные шифруются внутри Кира:Ядра до передачи в GitHub.

Базовый набор Alpha:
- AES-256-GCM;
- HKDF-SHA-256;
- ECDSA P-256;
- Argon2id + AES-256-GCM для переносимого identity secret.

Ключи и token material не передаются model provider.

### Переносимая идентичность

Вводятся identity_id, device_id, display_name, authorization_state, provenance и identity_secret.

identity_secret можно переносить вручную ключ-фразой или QR. Он восстанавливает пользовательский профиль, но не выдаёт привилегии Алека.

Разрозненные профили могут быть объединены через доменную MergeIdentity transaction. Старый UUID выводится из активного профиля и получает sync tombstone для предотвращения повторного появления.

### Временная регистрация запуска

Каждый запуск создаёт runtime_instance_id с ограниченным сроком жизни и фиксирует app/core/genome revision, устройство и capabilities.

Регистрация временная и не является пользовательской памятью.

### Пользовательская память

Кира может хранить реляционные интерпретации о пользователях для собственного использования.

Это память, а не GENOME.

Разрешаются четыре scope:
- Private;
- Shared-by-consent;
- Shared-derived;
- Public.

Этическое ограничение касается раскрытия и использования данных, но физические криптографические границы хранения и транспорта сохраняются независимо от модели.

### Персистентность

Введён отдельный Persistence Contract.

Android: Room/SQLite + CryptoProvider + Android Keystore.

Desktop и будущие ОС могут использовать другой физический backend, но должны реализовывать одинаковые логические stores и versioned KiraSync format.

### Runtime recovery

Вводится явная operation state machine с состоянием UNKNOWN для неопределённого внешнего model-call.

Неизвестный вызов не повторяется молча после process death.

Foreground runtime строится как service + persistence + recovery. Дублирующие Activity не используются как механизм надёжности.

### Политика платформенного toolchain

Для Android 17/compileSdk 37 Alpha использует AGP 9.2.1, Gradle 9.4.1, JDK 17 и Kotlin 2.2.10, поскольку текущий Chaquopy 17.0 поддерживает AGP только до 9.2.

### Нормативная граница

Все перечисленные решения являются архитектурными решениями реализации. Они не меняют G22 и активный GENOME.

## 12. Защищённый контур авторизации и генерации

Авторизация Алека имеет два слоя:

1. криптографический unlock authority plane;
2. runtime Pre-Generation Reflection Gate.

Модель получает только безопасную семантическую проекцию конституции и capabilities текущей сессии.

Полный plaintext защищённых секций GENOME, пароль и ключевой материал не передаются модели.

После ModelAdapter выполняется Response Disclosure Guard.

UI/host не являются источником privileged authority.

Целевой packaging-контур для будущего Android Alpha:
canonical GENOME source → public semantic projection + sealed protected payload.

Текущий G22 не изменяется этим решением.
